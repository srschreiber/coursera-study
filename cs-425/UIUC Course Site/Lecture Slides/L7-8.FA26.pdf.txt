 Ping-Pong

    Ping (0x00)                                        Pong (0x01)
             no payload                                 Port ip_address Num. files shared Num. KB shared

Goal: keep neighbor lists fresh despite peers joining, leaving and failing
Peers initiate Ping’s periodically
Pings flooded out like Querys
Pongs routed along reverse path like QueryHits
Pong replies used to update set of neighboring peers
List size specified by user at peer
      •   Heterogeneity: some peers may have more neighbors
      •   Gnutella found to follow power law distribution                                                  34

  To avoid duplicate transmissions, each peer maintains a list of recently received messages

Gnutella Problems

• Ping/Pong constituted 50% traffic
   • Solution: Multiplex, cache and reduce frequency of pings/pongs

• Repeated searches with same keywords
   • Solution: Cache Query, QueryHit messages

• Modem-connected hosts do not have enough bandwidth
   • Solution: use a central server to act as proxy for such peers
   • Another solution: FastTrack System (see Additional slides)

 BitTorrent: Policies

File split into blocks (32 KB – 256 KB)
Download Local Rarest First block policy:
      Prefer early download of blocks that are least replicated among neighbors
      Exception: New node allowed to pick one random neighbor: helps in bootstrapping
      Local and not global – decentralized
Tit for tat bandwidth usage:
      Provide blocks to neighbors that provided it the best download rates
      Incentive for nodes to provide good upload rates
      Discourages freeloading
Choking: Limit number of neighbors to which concurrent uploads (e.g., 5) i.e., the “best” neighbors
       Everyone else choked
       Periodically re-evaluate this set (e.g., every 10 s) to see if the best peers have changed
Optimistic unchoking
       periodically (e.g., ~30 s), unchoke a random choked neighbor (need not be best)
       helps discover better peers                                                                    40

   Analysis (contd.)

Search takes O(log(N)) time
   Proof

Stabilization Protocol

   Chord peers periodically run a stabilization algorithm that checks and updates
   pointers and keys
   •   Ensures non-loopiness of fingers, eventual success of lookups and
       O(log(N)) lookups w.h.p.

   Periodically, ask your successor for its predecessor.
         • If that node lies between you and your successor, make it your new
           successor

   How to update fingertable entries?
         • Route a query to (n+2i) mod 2m

•   Similar set of operations for dealing with
    peers leaving
     •   For dealing with failures, also need failure
         detectors (you’ve seen them!)

Virtual Nodes

•   Hash can get non-uniform ➔ Bad load balancing
     • Treat each node as multiple virtual nodes
        behaving independently (typically O(log N))

     • Each virtual node maps to a point in the ring

     • Reduces variance of load imbalance

                                                       83

Churn

•   When nodes are constantly joining, leaving, failing
     •   Leads to excessive (unnecessary) key copying
     •   Stabilization algorithm may need to consume more bandwidth to keep up
           • Strong stability takes O(N^2) stabilization rounds
           • For more see [Extended paper on Chord webpage]

     •   Main issue is that files are replicated, while it might be sufficient to replicate only
         meta information about files
     •   Alternatives
           •   Introduce a level of indirection, i.e., store only pointers to files (any p2p system)
           •   Replicate metadata more, e.g., Kelips (later in this lecture)

           • Choose log N neighbors intelligently
           • You could modify Chord to do this

       • Can we reduce the number of hops? – Kelips.

Pastry Neighbors

•   Routing tables based on prefix matching
     • Think of a hypercube
•   Routing is thus based on prefix matching, and is
    thus log(N)
     • And hops are short (in the underlying
        network)

•   Consider a peer with id 01110100101.
•   Peer maintains a neighbor peer with an id matching each of the
    following prefixes (* = starting bit differing from this peer’s
    corresponding bit):
      • *
      • 0*
      • 01*
      • 011*
      • … 0111010010*

Pastry Routing

•   Consider a peer with id 01110100101.
•   Peer maintains a neighbor peer with an id matching each of the
    following prefixes (* = starting bit differing from this peer’s
    corresponding bit):
      • *
      • 0*
      • 01*
      • 011*
      • … 0111010010*
•   When it needs to route to a peer, say 01110111001, it starts by
    forwarding to a neighbor with the largest matching prefix, i.e.,
    011101*
      • Hypercube routing

                                                                       10

Pastry Locality

•   For each prefix, say 011*, among all potential
    neighbors with the matching prefix, the neighbor
    with the shortest round-trip-time is selected
•   Since shorter prefixes have many more
    candidates (spread out throughout the Internet),
    the neighbors for shorter prefixes are likely to be
    closer than the neighbors for longer prefixes
•   Thus, in the prefix routing, early hops are short
    and later hops are longer
•   Yet overall “stretch”, compared to direct Internet
    path, stays short
